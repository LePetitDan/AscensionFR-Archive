Ces textes **font vraiment 10 caractères ou moins**, dans le jeu comme au banc — ils n'ont
aucune variable, il n'y a rien à simuler. La porte `len > 10` du module les décline pour de
bon. L'instrument ne les inventait pas ; il les rangeait au mauvais endroit.

La séparation est nette :

| | |
|---|---|
| DE **sans aucune variable** — court partout | **57** |
| DE **avec variable** — le bouchon du simulateur pouvait mentir | **8** |

#### Le vrai défaut, sur 8 entrées

Le bouchon numérique du simulateur vaut `34`, deux caractères :

```
DE = '+$s1 Armor.'   →   simulé '+34 Armor.'   =  EXACTEMENT 10 caractères
```

Une valeur d'armure réelle en fait `+1350 Armor.`, soit 12 : **le module la traduit très bien.**
Le banc comptait donc un échec que le jeu n'a pas, pour un seul caractère manquant.

#### La correction

Deux principes, et le second est celui qui compte :

1. **Rejuger avec une valeur plausible, pas remplacer le simulateur.** Rebâtir toute la ligne de
   base des hachages pour huit entrées aurait coûté plus que le défaut. Seuls les affichés
   ≤ 10 caractères sont resimulés.
2. **Le classement se fait tout seul.** Un texte court par nature n'a pas de variable : il
   ressort identique de la seconde simulation, reste sous la porte, et se range de lui-même
   dans `court_par_nature`. Aucune liste d'exceptions à tenir à jour.

**Et j'ai failli mentir dans l'autre sens.** Mon premier « plausible » était un bouchon à 4
chiffres, qui déclarait récupérées deux entrées en `${…}`. Or ce ne sont pas des nombres à
deviner, ce sont des **expressions arithmétiques calculables** :

| | valeur calculée | affiché | verdict juste |
|---|---|---|---|
| `+${4.4*$PL} Armor` | 4,4 × 80 = **352** | `+352 Armor` = 10 car. | **reste court** — le module le décline vraiment |
| `+${27*$PL} Armor` | 27 × 80 = **2160** | `+2160 Armor` = 11 car. | **récupéré** — le banc l'accusait à tort |

Le simulateur évalue maintenant ces expressions (`$PL`=80, `$AP`/`$RAP`=2000, `$SP`=1500). Un
banc qui fabrique des succès est aussi menteur qu'un banc qui fabrique des échecs.

**Troisième correctif, trouvé en chemin** : le contrôle de non-régression ne guettait que
`traduit → anglais`. Avec un verdict de plus, un `traduit → court_par_nature` serait passé
inaperçu alors que c'est la même perte à l'écran. La règle est maintenant : perdre un
« traduit », **quel que soit** le verdict qui le remplace.

#### Re-taguer `v3.4.0` sans casser les téléchargements

C'est le point qui t'inquiétait le plus. **La bonne nouvelle d'abord : le Hub des joueurs ne
pointe sur aucune URL de tag.**

```python
API_RELEASE = "https://api.github.com/repos/" + DEPOT + "/releases/latest"
```

Il interroge `releases/latest` à chaque fois et résout la release courante. **Un joueur dont le
Hub tourne aujourd'hui ne voit strictement aucune différence** : il redemande `latest`, obtient
la même release `v3.4.0`, les mêmes deux assets.

Les assets, eux, sont attachés à l'objet **release** et adressés par *nom de tag + nom de
fichier* :

```
https://github.com/LePetitDan/AscensionFR/releases/download/v3.4.0/AscensionFR_Compagnon.exe  (37,9 Mo)
https://github.com/LePetitDan/AscensionFR/releases/download/v3.4.0/AscensionFR_manuel.zip     (27,9 Mo)
```

**Déplacer le tag ne touche ni la release ni ses assets** : elle est identifiée par le NOM du
tag, pas par le commit visé. Ce qui change — et c'est précisément ce qu'on veut — ce sont les
liens « Source code (zip / tar.gz) », que GitHub recalcule depuis la cible du tag.

> 🛑 **Le geste à ne JAMAIS faire : supprimer le tag.** `git push origin :refs/tags/v3.4.0`
> repasse la release en **brouillon** côté GitHub. À cet instant : les deux URL de
> téléchargement renvoient 404, et `releases/latest` retombe sur `v3.3.1` — chaque Hub
> proposerait à son joueur une « mise à jour » **vers l'arrière**. C'est le seul scénario qui
> casse quelque chose, et il est évitable.

Le geste juste est un **déplacement**, jamais une suppression :

```bash
git push --force origin <sha-du-nouveau-commit>:refs/tags/v3.4.0
```

**Et je propose de le répéter à blanc avant de le faire pour de vrai** — sur un tag jetable
(`v0.0.0-essai`) : créer une release d'essai avec un petit asset, déplacer le tag, vérifier que
l'URL de l'asset répond toujours, puis tout supprimer. Trente secondes, zéro risque, et on ne
découvre pas le comportement de GitHub sur la release que les joueurs utilisent. C'est la même
leçon que l'affaire du `--dry-run` qui n'existe pas.
